Please have a look at this UI heirarchy. It is like a directory of options for the LTO System console application. For each endpoint of the options, I have also indicated their the views and stored procedures that I think I would need for this application to properly work.

Now, my reason for creating this is that I think that the whole "lto_system" repository is messy in terms of code. Blocks of codes are not segregated according to the intended function of their respective Python programs. 

My resolution is to create a better SQL_Statements file (modifying only the Views and Stored Procedures so that my database schema remains unchanged). These views and stored procedures would then be used for getting the data for what the UI option intends.

Now, since there are heirarchy of options in the console app UI, I think it would be better to define functions for printing these options and getting/validating input from the user. So, in a sense, a function prints the options and gets input from the user, this input is validated, and another function is called for executing the optiong that the input is for.
